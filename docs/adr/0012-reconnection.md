# ADR 0012: 재접속 — 방장 복구, 게스트 재입장, 끊김 내성

## 상태
채택 (2026-10). 코어(규칙이 켜진 메모리 Firestore), 실제 Firebase SDK + 에뮬레이터, 화면(Robolectric)에서 검증했다.

## 맥락
방장 기기 권위 모델(설계 §8)에서 한 판은 방장 앱이 살아 있어야 진행된다. 지금까지는 앱이 꺼지거나 화면을 나가면 그 판으로 돌아올 길이 없었고,
일시적인 전송 오류 하나로 게임이 영영 멈출 수 있는 곳이 있었다.

## 결정
1. **방장 복구(`GameLauncher.resumeHost`)**: 방장은 게시할 때마다 좌석별 뷰와 함께 **권한자 백업**(`authority/state`, 방장만 읽음)을 같은 배치로 쓴다.
   앱을 다시 켜면 백업을 읽어 `HostGameSession`을 다시 연다. 좌석은 백업의 순서 + 방의 좌석 정보(`GameStartPlan.resume`)로 만든다 — 진행 중에는 방 좌석이 바뀔 수 없다.
   백업 = 게스트가 본 마지막 상태이므로, 그 뒤 방장 기기에서만 일어난 일은 잃어도 아무도 모른다. 게임 문서가 FINISHED면 이어 갈 것이 없으므로 null(-> 방을 대기 상태로 돌린다).
   방장이 없는 동안 게스트가 보낸 명령은 PENDING으로 남아 있다가 복구 직후 처리된다(맞는 버전이면 적용, 아니면 STALE_VERSION).
2. **대기실이 게임으로 이어 준다(`WaitingRoomModel`)**: 방이 PLAYING이고 내가 앉아 있으면 들어간다 — 게스트는 `join`, 방장은 `resumeHost`.
   방장이 **지금 시작하는 중**(`starting`)이면 복구로 착각하지 않는다(방 시작 트랜잭션과 게임 ID를 아는 순간 사이의 틈). 수동으로는 `rejoin()`("게임으로 돌아가기").
   `gameInProgress`로 화면이 버튼을 보인다.
3. **앱 재시작 -> 그 방으로(`ActiveRoomStore`)**: 들어간 방을 계정별로 기기에 기억한다(SharedPreferences). 멀티플레이를 열면 그 방이 아직 있고 내가 앉아 있을 때 그 방으로 가고,
   대기실이 게임을 이어 준다. 방이 없거나 닫혔거나 내가 없으면 기억을 지운다. 확인할 수 없으면(네트워크) 기억을 두고 로비를 보인다. 다른 기기에서 이어 하기는 하지 않는다.
4. **끊김 내성(런타임)**
   - 방장: 게시가 실패하면 **최신 상태를 성공할 때까지 다시 게시**한다. 다음 상태 변경을 기다리면, 모두가 그 상태를 보고 움직여야 하는 경우(게스트 차례) 영영 멈춘다.
     게시는 자물쇠로 한 번에 하나 — 옛 게시가 새 게시 뒤에 도착해 뷰를 되돌리지 않게. 결과 기록은 **실제로 쓴 뒤에만** 완료로 표시한다(전에는 쓰기 전에 표시해서 실패하면 결과가 영영 없었다).
   - 게스트: 뷰·연결 구독이 오류로 끊기면 잠시 뒤 다시 구독한다(전에는 코루틴이 조용히 죽어 화면이 멈췄다). 연결 상태 = 방장 생존 신호 + 뷰 구독이 살아 있는가.
5. **화면**: 게임 화면에 연결 배너(다시 연결 중 / 방장과 끊김 + "대기실로"), 대기실에 "게임으로 돌아가기", 멀티플레이 게임에서 **뒤로 가기는 기권 확인**(결과 뒤에는 나가기).
   방장과 끊겨 대기실로 나온 게스트는 방장이 돌아오면 버튼으로 다시 들어간다.

## 테스트가 찾은 것 (모두 수정됨)
- **제품: `RemoteGameSession`의 새 필드를 `init` 뒤에 선언** -> `init`에서 띄운 코루틴이 다른 스레드에서 초기화 전의 자물쇠(null)를 만나 NPE로 죽고 게스트 화면이 멈췄다. 필드를 `init` 앞으로.
- **제품: 게임 시작을 알린 뒤에 "여는 중"을 풀었다** -> 받는 쪽이 곧바로 다시 들어가기를 누르면 무시됐다. 알리기 전에 푼다.
- 결과 기록 완료 표시 순서(위 4).
- 테스트 도구: 변이 검증이 **컴파일 실패를 "살아남음"으로 셌다**(경고=오류인 코어에서 쓰지 않는 변수). 컴파일 오류를 따로 세고, 그 변이들을 컴파일되는 형태로 다시 확인했다.
  그중 "시작 중 복구 착각" 보호는 틈이 너무 짧아 잡히지 않았다 -> 방 시작 트랜잭션 뒤에 지연을 넣은 테스트로 틈을 벌려 결정적으로 검증.

## 검증
- 런타임 +3(다시 게시해서 게스트가 따라잡음, 결과 기록 재시도, 게스트 재구독). 변이 4종 검출.
- `:shell` `ReconnectTest` 6개: 방장 앱 종료 -> 복구 -> 끝까지 + 정산(레이팅 표대로), 게스트 앱 종료 -> 재입장, 화면을 나온 게스트의 `rejoin`, 게임이 없으면 아무 일 없음,
  끝난 게임 뒤 꺼진 방장 -> 방을 대기 상태로, 시작 중 복구 착각 없음. 변이 4종 검출. `:shell`+`:runtime` 10회 반복 0건 실패.
- 에뮬레이터 1개: 실제 규칙에서 방장 앱 종료 -> 새 인스턴스(빈 캐시)로 다시 로그인 -> 백업 읽기 -> 같은 버전 다시 게시 -> 끝까지 -> 끝난 게임은 다시 열지 않음.
- 화면 4개: 게스트 앱 재시작 -> 멀티플레이를 열자마자 그 게임으로, 방장과 끊김 배너 -> 대기실 -> 방장 복구 -> 게임으로 돌아가기 -> 배너 사라짐,
  방장(봇과) 앱 재시작 -> 복구, 뒤로 가기 -> 기권 확인. 변이 6종 검출. 앱 멀티플레이 묶음 6회 반복 0건 실패.

## 한계 / 다음
- **방장 이전(host migration)은 없다**: 방장이 돌아오지 않으면 그 판은 끝나지 않는다(게스트는 대기실로 나와 다른 방으로 갈 수 있다. 결과가 없으므로 레이팅 영향 없음).
  방은 PLAYING으로 남는다 — 서버 정리(Cloud Function/TTL)는 Phase 7.
- 방장이 없는 동안에는 시간 제한도 멈춘다(마감은 방장이 계산한다). 복구하면 새 마감으로 다시 시작한다.
- 앱 재시작 복귀는 같은 기기에서만(방 기억이 기기에 있다). 게임 중 방장이 기권해도 방장 앱은 끝까지 권위자로 남아야 한다(화면을 닫으면 다른 사람의 판이 멈춘다).
