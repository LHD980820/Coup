# ADR 0015: 서버 판정 — 검증형 방장 권위

## 상태
채택 (2026-10, 오너 결정: "검증형 방장 권위"). 코어 모델·실제 규칙(에뮬레이터)·실제 Firebase Android SDK·서버 클라이언트 라이브러리(에뮬레이터)·로컬 함수 실행기에서 검증했다.
**실제 배포(Blaze 요금제, Cloud Functions 2세대)는 오너 작업이다** — 아래 "배포".

## 맥락
- 지금까지 방장 기기가 게임을 돌리고(ADR 0005) 결과를 쓰며, 각 플레이어가 자기 레이팅을 반영했다(ADR 0007).
  규칙은 "잘못 반영"은 막았지만 **방장의 순위 조작**과 **진 게임 반영하지 않기**는 막지 못했다. 후자는 정산 게이트(`pendingRatings`)로 완화했었다.
- 선택지: (1) 서버가 게임을 직접 돌린다(모든 수가 함수 호출 -> 비용·지연·코드 대이동), (2) **방장은 그대로 돌리고 모든 수를 기록, 서버가 끝난 판을 다시 돌려 검증**(검증형 방장 권위), (3) 지금 그대로.
  오너가 (2)를 골랐다.

## 결정
1. **기록**(1단계). 권한자(`GameAuthority`)가 적용한 명령을 하나도 빠짐없이 `AppliedCommand(version, command, source = SEAT|TIMEOUT, ref)`로 남기고,
   방장 세션이 뷰·백업과 **같은 배치**로 `games/{id}/log/{version}`에 쓴다. 규칙: 방장만 만들기, 문서 ID = 버전, `at == request.time`(서버 시각, 꾸밀 수 없다), 수정·삭제 불가, 방장만 읽기(교환 카드 등 비공개 정보).
   게스트의 수는 `ref` = 그 게스트가 쓴 명령 문서 ID. 게시가 실패하면 기록도 다음 게시에 다시 담는다(이미 쓴 것은 빼고 — 처음 시각 유지).
2. **고정된 출발점**. 시드·좌석 순서·룰셋 = `games/{id}/authority/setup`은 **게임 문서를 만드는 같은 배치에서만** 만들 수 있고 고칠 수 없다(판이 진행된 뒤 결과에 맞는 시드를 골라 넣지 못하게).
   게임 문서의 `createdAt` = 서버 시각. 방장은 게임 문서의 `status`·`version`·`hostHeartbeatAt`만 바꿀 수 있다(좌석·rated·시작 시각·판정 불변).
3. **검증기**(`core/judge`, 순수 Kotlin `GameVerifier`): 실행 설정부터 기록을 같은 엔진으로 다시 돌린다. 확인하는 것:
   - 설정이 게임 문서와 맞는다(같은 게임, 같은 룰셋, 사람 좌석 전원 포함, 방장 착석, 중복 없음, rated면 봇·하우스룰 없음) — `SETUP_MISMATCH`/`NO_SETUP`
   - 기록이 1부터 빈틈없다 — `LOG_GAP`. 모든 수가 그 시점에 합법이다 — `ILLEGAL_COMMAND`. 좌석에 있는 사람의 수다 — `UNKNOWN_ACTOR`
   - 게스트의 수는 **그 게스트가 직접 쓴 명령 문서**에 묶여 있고(보낸 사람 = 수의 주인, 버전 조건을 뺀 내용이 같다, 한 문서는 한 번만) — `FORGED_GUEST_COMMAND`
   - 시간 초과는 엔진의 기본 수 그대로이고, 결정이 있던 사람이며, 게스트라면 결정이 시작된 뒤(서버 시각) 정해진 시간 − 여유 3초가 지났다 — `BAD_TIMEOUT`/`EARLY_TIMEOUT`.
     결정 시작은 권한자와 같은 기준(같은 턴의 같은 요청이 이어지는 동안 같은 결정, 첫 결정은 게임 문서의 `createdAt`)
   - 판이 끝났고 순위가 결과 문서와 같다 — `NOT_FINISHED`/`RANKING_MISMATCH`
   변동량은 결과 문서의 값이 아니라 **다시 돌린 순위로 서버가 계산**한다.
4. **판정·반영**(`ServerJudge`, 관리자 권한 `DocumentStore`). 결과 문서가 생기면: 게임에 판정이 이미 있으면 끝(중복 이벤트 안전). 비레이팅이면 `UNRATED` 표시만.
   검증을 통과하면 **한 트랜잭션**으로 참가자 전원의 프로필(레이팅·판수·승수) + 반영 표시(`appliedResults`)를 쓰고(형식은 예전 클라이언트 반영과 같다 — `UserDocuments`),
   옛 정산 대기 표시가 이 판을 가리키면 지우고, 게임 문서에 `verdict = VERIFIED`(+ `judgedAt` 서버 시각). 실패하면 `REJECTED` + 사유, **아무의 레이팅도 바꾸지 않는다**.
5. **규칙 전환**(3·4단계). 클라이언트는 레이팅·반영 표시를 쓸 수 없다(본인 프로필은 닉네임만). 판정은 서버만 쓴다.
   **정산 게이트를 없앴다**: 서버가 모두의 레이팅을 반영하므로 "진 게임 반영하지 않기"가 불가능하다 — 방 만들기·입장·게임 생성의 `isSettled`, 방장의 대기 표시 쓰기, `RoomError.UNSETTLED_GAME`을 지웠다.
   `pendingRatings`는 클라이언트가 읽고 쓸 수 없고(전부 거부 경로), 서버가 남은 것을 정리한다. 결과 문서의 순위 = 사람 좌석 전원, 변동량 = 표 검사는 남겼다(결과 화면이 보여 주는 값).
6. **클라이언트는 지켜본다**. `FirestoreUserRepository.observeSettlement(gameId)`: 게임 문서의 판정 + 내 반영 표시를 함께 보고 `Verifying / Applied(record, rating) / Unrated / Rejected / NotApplied`.
   판정은 "검증됨"인데 표시 구독이 아직 안 왔으면 서버에서 다시 읽는다(서버는 둘을 한 트랜잭션으로 쓰지만 구독은 따로 도착한다). 비레이팅 판은 서버를 기다리지 않는다.
   `AccountSession.watchSettlement`가 판정이 날 때까지 구독하고(끊기면 다시), 결과 대화상자는 "서버가 결과를 확인하는 중… / 레이팅 n (±d) / 레이팅 제외 / 확인하지 못해 반영되지 않음".
   앱이 꺼져도 반영은 서버가 하므로 잃는 것이 없다(예전의 "다음 접속 때 정산"이 필요 없다).
7. **Cloud Function**(`server/`, 따로 빌드하는 Gradle 빌드, `includeBuild("../core")`): `JudgeFunction`(2세대, Java 21 런타임, `CloudEventsFunction`)이
   `google.cloud.firestore.document.v1.created` / `document=results/{gameId}` 이벤트의 **주제(subject) 경로만** 읽고 `ServerJudge`를 돌린다(이벤트 본문 protobuf는 읽지 않는다).
   `AdminDocumentStore`는 Google Cloud Firestore 서버 클라이언트 위에 앱 어댑터(ADR 0009)와 같은 의미(최상위 필드 병합, 서버 시각, 밀리초)를 지킨다. 결과·게임이 아직 안 보이면 예외 -> 재시도(`--retry`).
   배포물은 의존성을 모두 담은 JAR 하나(Shadow, gRPC 서비스 파일 병합).

## 검증
- `:judge` 31(판정 25 + 검증기 6): 실제 한 판(방장 권위 세션 + 원격 게스트, 규칙이 켜진 FakeFirestore)을 끝내고 판정 -> 검증·반영·정산 대기 정리·중복 판정 무시, 게스트 시간 초과만으로 둔 판(3인 — 응답 창에서 연달아 시간 초과),
  첫 결정이 게스트인 판, 비레이팅, 결과 없음, 점검(`inspect`)은 쓰지 않음. 조작 15종 각각이 정해진 사유로 거부되고 레이팅 불변:
  순위 바꾸기, 없는 명령 문서·남의 명령 문서·공범이 피해자 이름으로 쓴 문서·다른 내용·한 문서 두 번·연결 지우기, 기록 하나·마지막 기록 지우기, 엔진이 받지 않는 수, 좌석 밖 사람, 실행 설정 없음·시드 바꾸기·룰셋 다름·사람 빼기·레이팅 판의 하우스룰,
  이른 시간 초과(게임 시작 기준 포함), 기본 수가 아닌 시간 초과, 결정 없는 사람의 시간 초과, 제한 없는 결정의 시간 초과. 검증기 단위 6(봇이 있는 비레이팅 기록의 설정 검사).
  **변이 22종 중 21종 검출**, 살아남은 1종(재생 버전 = 기록 버전 검사)은 엔진이 수마다 버전을 정확히 1 올리므로 빈틈 검사와 같다(중복 방어로 남김).
- 규칙: 모델 재생 시나리오 66개·판단 2,703건 불일치 0, 규칙 변이 86개 중 71개 검출(15개는 중복 방어 — `firebase/README.md`). 클라이언트의 정확한 레이팅 반영·표시만 쓰기·표시 수정/삭제·판정 쓰기·대기 표시 읽기/쓰기 모두 거부. 옛 대기 표시가 있어도 방·게임 가능.
- 셸·앱: 대기실에서 시작한 3인 판, 방장 앱이 꺼졌다 백업에서 이어 간 판(**방장이 바뀐 기록도 검증된다**), 앱 화면의 레이팅 줄이 테스트용 서버 판정(`launchJudge`, `:judge` testFixtures)으로 반영된다.
- 실제 Android SDK(에뮬레이터, `:data`): SDK가 쓴 기록(서버 시각 Timestamp)이 `ServerJudge.inspect`로 **검증된다**. 표대로인 클라이언트 반영과 방장의 판정 쓰기는 거부, 판정 전에는 "확인 중".
- 서버(`server/`, 에뮬레이터 + 서버 클라이언트 라이브러리) 5: 저장소 의미(필드 병합·서버 시각·트랜잭션·정렬/조건 쿼리), 한 판 -> 이벤트 -> 전원 반영 + 재전송 무시, 순위 조작 -> 무효·불변, 다른 문서 무시·결과 없으면 재시도.
  배포 JAR을 Google의 로컬 함수 실행기(`java-function-invoker`)에 올려 Firestore 이벤트(HTTP 바이너리 CloudEvent)를 넣어 봤다: 무관한 문서 200, 결과 없음 500(재시도).
- CI `firebase-emulator` 작업이 서버 테스트와 배포 JAR 빌드도 돈다.

## 배포 (오너 작업)
1. Firebase 프로젝트를 **Blaze**(종량제)로 바꾼다. Cloud Functions·Eventarc·Cloud Build·Artifact Registry·Cloud Run API를 켠다.
2. `cd server && ./gradlew stageDeploy` -> `server/build/deploy/coup-judge.jar` 하나.
3. 배포(리전은 **Firestore 데이터베이스 위치와 같게** — Firestore 트리거의 요구):
   ```
   gcloud functions deploy coup-judge --gen2 --runtime=java21 --region=<Firestore 위치> \
     --source=server/build/deploy --entry-point=io.github.lhd980820.coup.server.JudgeFunction \
     --trigger-event-filters=type=google.cloud.firestore.document.v1.created \
     --trigger-event-filters=database='(default)' \
     --trigger-event-filters-path-pattern=document='results/{gameId}' \
     --retry --memory=512Mi
   ```
   함수의 서비스 계정에 Firestore 읽기·쓰기(`roles/datastore.user`)가 있어야 한다(기본 컴퓨트 서비스 계정은 보통 이미 있다).
4. **규칙과 앱을 같은 때 배포한다**: 새 규칙은 클라이언트의 레이팅 반영을 막으므로, 함수 없이 규칙만 올리면 레이팅이 멈춘다. 순서: 함수 -> 규칙 -> 앱.
5. 확인: 테스트 계정 둘로 레이팅 판 하나 -> 함수 로그 `game …: verified, ratings applied to […]`, 결과 화면의 레이팅 줄.

## 결과와 한계 (남는 위험)
- **방장이 남의 패를 보는 것**은 막지 못한다(권한자 상태가 방장 기기에 있다). 오너가 받아들인 위험.
- 방장이 **게스트의 명령을 일부러 처리하지 않기**: 게스트에게는 시간 초과와 같다(서버는 정해진 시간이 지났는지만 본다). 무제한 결정(사람 응답 무제한 정책)이면 판이 끝나지 않을 뿐이다.
- 방장이 판을 여러 번 새로 시작해 좋은 패를 고르기: 시드는 게임 생성 때 고정되지만 방장은 시작 전에 시드를 안다. → **ADR 0016**: 시드에 서버 생성 시각을 섞는다.
- 시간 검사는 방장 기기 시계가 아니라 **기록이 서버에 닿은 시각**으로 한다. 게시가 늦게 닿으면 시간 초과가 실제보다 늦어 보일 뿐(통과 방향), 일찍 보이지는 않는다 — 여유 3초는 결정 시작 쪽 지연을 덮는다.
- 끝나지 않은 판(방장이 사라짐)은 결과가 없으므로 판정되지 않는다. → **ADR 0016**: 10분 넘게 멈춘 판은 서버 정리가 끝내고 방장만 패배로 반영, 버려진 방도 닫는다.
- 비용: 수마다 기록 문서 1건 추가 쓰기. 판정은 판마다 함수 1회 + 기록 수만큼 읽기.
- 함수가 배포되지 않았거나 실패하면 결과 화면은 "확인 중"에 머문다(재시도·로그로 확인). 서버 쪽 오류 알림은 후속.
