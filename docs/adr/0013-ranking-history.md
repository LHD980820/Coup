# ADR 0013: 랭킹·전적 화면

## 상태
채택 (2026-10). 코어 모델(규칙이 켜진 메모리 Firestore), 실제 규칙(에뮬레이터), 화면(Robolectric)에서 검증했다.

## 결정
1. **코어(`:shell`/`stats`)**: `RankingModel`(상위 N명 + 내 프로필을 합쳐 `MyStanding` = 상위 안 / 상위 밖 / 아직 순위 없음), `HistoryModel`(내 rated 기록 + 프로필 -> 승률, 보이는 기록의 레이팅 변화 합).
   둘 다 기존 `FirestoreUserRepository.observeTop/observeHistory/observeProfile`을 구독하고, 구독이 오류로 끊기면 `offline`을 켜 이미 받은 목록은 그대로 두고 잠시 뒤 다시 구독한다.
   정렬·공동 순위·"한 판도 안 한 사람 제외"는 `:account`의 `Rankings`가 그대로 한다.
2. **앱**: `RankingScreen`(내 자리 카드 + 순위 목록, 내 줄 강조), `HistoryScreen`(요약 + 최근 기록: n인전 · 순위, 날짜, 레이팅 변화 색 구분 + 접근성 설명). 홈의 프로필 카드에서 연다(로그인한 때만).
   로그아웃하면 이 화면들에서 홈으로 돌아간다. `SignedIn`이 `FirestoreUserRepository`를 함께 가진다.
3. 문구는 ko/en, 번역 누락은 `MultiplayerTextsTest`가 잡는다.

## 검증
- `:shell` +7(순위·공동 순위·미플레이 제외, 상위 안/밖, 변화 따라가기, 오프라인 복구, 전적 요약, 빈 전적): 변이 5종 검출.
- 에뮬레이터 +2: 실제 정렬 쿼리가 규칙을 통과하고 내 순위를 찾는다, 내 전적은 최근 것부터 읽히고 **남의 전적은 PERMISSION_DENIED**.
- 화면 +7 + 문구 1: 순위 순서·공동 순위·내 자리 안내·실시간 갱신·빈 안내, 전적 순서·요약·부호·빈 안내, 로그아웃. 변이 6종 검출.

## 한계
- **서버는 레이팅 순으로 N명만 주고 한 판도 안 한 사용자는 그 뒤에 거른다.** 레이팅 1000의 신규 계정이 많아지면 상위 N명 안에 플레이한 사람이 N명보다 적게 남을 수 있다.
  근본 해결은 `plays > 0` 조건 + 복합 색인(`firestore.indexes.json` 배포) 또는 서버 집계(Phase 7)다. 지금은 레이팅이 1000보다 높은 사람이 먼저 오므로 실제 영향은 낮은 레이팅 구간에서만 보인다.
- 랭킹은 상위 50명만 본다(내가 밖이면 내 레이팅만 보인다). 친구/기간별 랭킹, 전적 상세(상대·판 다시 보기)는 후속.
- 레이팅은 아직 클라이언트가 반영한다(Phase 7 전까지, ADR 0007) — 랭킹은 규칙이 막지 못하는 "반영하지 않기"의 영향을 받는다.
