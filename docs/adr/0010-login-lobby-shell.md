# ADR 0010: 로그인·로비 UI의 구조 (`:shell` 코어 모듈 + 화면은 얇게)

## 상태
채택 (2026-10). 코어 모델은 규칙을 강제하는 메모리 Firestore로, 인증 어댑터는 Auth 에뮬레이터로, 화면은 Robolectric + Compose로 검증했다.

## 맥락
- Phase 3의 남은 일은 로그인 -> 로비 -> 대기실 -> 게임 화면이다. 규칙(`RoomRules`), 저장(`FirestoreRoomStore`), 전송(`FirestoreGameTransport`), 어댑터(`:data`)는 이미 있다.
- 이 화면들은 판단할 것이 많다(입력 검사, 방 상태에 따른 버튼, 게임 시작 순서, 정산). 화면에 두면 에뮬레이터 없이는 시험하기 어렵다.

## 결정
1. **새 코어 모듈 `:shell`(순수 Kotlin)** — 화면이 그릴 상태와 의도(intent)를 가진 모델들. 설계 §10.4의 `GameController`와 같은 방식이다.
   - `auth`: `AuthGateway`(인터페이스) + `AuthFormModel`(로그인·가입·비밀번호 재설정 한 폼, 입력 검사는 제출 뒤에만 보이고 고치면 사라짐, 중복 제출 무시).
   - `account`: `AccountSession`(로그인 직후 프로필 만들기·옛 계정 이어받기·정산 대기 반영, 끝난 게임 `settleGame` — 결과 문서가 늦게 쓰이므로 기다리며 재시도).
   - `lobby`: `LobbyModel`(방 목록을 주기적으로 읽기, 만들기·입장·코드 입장, 실패는 `RoomError`/네트워크로 구분), `WaitingRoomModel`(방 구독, 준비·봇·내보내기·규칙·시작, 쫓겨남/방 닫힘 감지),
     `GameLauncher`(방장은 게임 문서를 만들고 세션을 열고, 게스트는 게임 문서가 보일 때까지 기다렸다가 붙는다).
   - 모든 모델은 `FakeFirestore`(규칙을 강제하는 메모리 저장소) 위에서 테스트한다 — **방 만들기 -> 입장 -> 준비 -> 시작 -> 3인 게임 -> 정산 -> 대기실 복귀**를 규칙이 켜진 채로 돈다.
2. **`FakeFirestore`를 `:remote`의 `testFixtures`로 옮겼다**(`java-test-fixtures`). `:shell`과 `:app` 테스트가 같은 접근 모델을 쓴다.
3. **인증 어댑터는 `:data`**(`FirebaseAuthGateway`): Firebase 오류를 `AuthError`로 바꾼다. 이메일 열거 보호가 켜진 프로젝트에서는 없는 계정과 틀린 비밀번호가 같은 `WRONG_CREDENTIALS`다.
   Auth 에뮬레이터 테스트 4개(가입·로그아웃·로그인, 실패 사유, 재설정 메일, 가입 직후 계정 준비가 실제 규칙을 통과).
4. **앱은 얇게**: `ShellViewModel`이 로그인 상태에 따라 서비스(`SignedIn`)를 만들고 없앤다. 서버 쪽 조립은 `Backend` 인터페이스 뒤에 있어(`FirebaseBackend` / 테스트의 `FakeBackend`)
   화면 테스트가 에뮬레이터 없이 돈다. 싱글플레이와 같은 `GameScreen`을 멀티플레이 세션으로 쓰고, 결과 대화상자에 레이팅 변화를 덧붙인다(반영 중 / 변화 / 반영 안 됨 / 지연).
5. **닉네임 편집은 대화상자가 아니라 프로필 카드 안에서 한다.** Robolectric에서 대화상자 안의 입력칸은 Compose를 영원히 유휴 상태로 두지 않았다(`AlertDialog` + `OutlinedTextField`만으로 재현).
   창을 하나 덜 띄우는 구조이기도 하다.
6. 문구는 `MultiplayerTexts`의 `when`으로 코어 값 -> 리소스를 잇는다(코어에 값이 늘면 컴파일이 막고), `MultiplayerTextsTest`가 모든 값의 ko/en 문구가 있고 서로 다른지 본다.

## 테스트가 찾은 것 (모두 수정됨)
- **제품: 계정 준비 상태와 프로필을 따로 받아 로비가 안 열릴 수 있었다.** "준비 완료"가 프로필보다 먼저 보이면 `openLobby`가 닉네임이 없어 아무것도 안 만들고 빈 화면에 멈췄다 -> 한 번에 받고(`combine`), 프로필이 늦으면 다시 시도.
- **제품: 방장의 명령 수신이 전송 오류 한 번에 영영 멈췄다.** 확인(ack) 쓰기나 구독이 실패하면 코루틴이 조용히 죽어 이후 모든 게스트 명령이 PENDING으로 남았다
  -> 확인 쓰기는 5번 다시 시도하고, 구독이 끊기면 다시 구독한다(`HostGameSession`, 테스트 2개).
- **테스트 도구: `FakeFirestore`가 배치를 `clear()` + `putAll()`로 적용해, 다른 스레드의 구독이 그 틈에 문서를 "없음"으로 읽었다** -> 방이 닫힌 것으로 오인하거나 명령을 놓쳤다(약 8%의 간헐 실패).
  바뀐 문서만 갱신하고 읽기를 같은 자물쇠 아래로 옮겼다. 이후 `:shell` 전체를 60회 반복해 0건.
- 테스트 틀: 범위 안에서 처리되지 않은 예외가 나면 테스트가 실패하도록 했다(조용히 죽은 코루틴을 놓치지 않게). 화면 테스트의 `waitFor`는 노드가 생긴 뒤 배치가 끝나기를 기다린다.
- 대기실의 `gameFinished`가 `endGame` 실패를 조용히 버리던 것을 문제로 보고하도록 고쳤다.

## 검증
- `:shell` 29개(인증 폼 8, 로비 7, 계정 5, 대기실 9): 변이 6종 모두 검출.
- 앱 화면 23개(인증·프로필·계정 준비 9, 방·게임 7, 문구 7): 변이 11종 모두 검출. 멀티플레이 테스트를 14회 반복해 실패 0건.
- 방장 UI + 봇으로 한 판(기권 -> "레이팅 제외" 안내 -> 대기실로), 게스트 UI가 목록에서 입장 -> 준비 -> 방장 시작 -> 게임 -> 기권 -> **레이팅이 표의 변동량대로 프로필에 반영** -> 대기실.

## 한계 / 다음
- 구글 로그인은 ADR 0011에서 추가했다.
- 게임 중 뒤로 가기/앱 종료 처리, 재접속(방장 기기 복구), 비공개 방 코드 복사/공유, 랭킹·전적 화면, 방 목록 알림은 후속 작업이다.
- 새 화면의 정식 진입점은 아직 디버그 런처("Coup (new)")다. 기존 로그인/홈 화면 교체는 Phase 5.
