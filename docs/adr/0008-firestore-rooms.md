# ADR 0008: Firestore 방 저장소와 방 규칙 (게임 좌석 동의 + 정산 게이트 연결)

## 상태
채택 (2026-10). 보안 규칙은 에뮬레이터 미검증(`firebase/README.md`).

## 맥락
- 로비 규칙(`RoomRules`, ADR 0006)은 순수 함수이고 저장소(`RoomStore.update`)가 원자성을 맡는다. Firestore 구현이 필요했다.
- ADR 0007의 정산 게이트는 방 입장 규칙에 `isSettled(uid)`를 연결해야 완성된다.
- 이전 규칙은 방장이 게임 문서 `seats`에 **아무 uid나** 넣을 수 있었다. 정산 게이트와 합쳐지면 남에게 가짜 rated 게임의 패배를 씌우고
  자동 정산을 강요할 수 있다(배포 전 필수로 막아야 할 구멍).

## 결정
1. **`DocumentStore.transaction`** 추가(읽기 -> 쓰기, 읽은 문서가 바뀌면 재실행 = Firestore 트랜잭션). `FirestoreRoomStore.update`는
   트랜잭션 안에서 `RoomRules` 변환을 적용한다 -> 마지막 자리 경쟁에서도 정확히 한 명만 들어간다(테스트: 커밋 직전 끼어들기).
2. **방 문서는 JSON 덩어리가 아니라 구조화된 필드**(`rooms/{id}`): 규칙이 "누가 어떤 필드를 바꿨는가"를 검사해야 하기 때문이다.
   - 사람 좌석: `members`(uid -> {name, readyVersion, seq}) + `memberOrder`(입장 순서). 봇: `bots` 목록. 룰셋: `ruleSet` 맵(하우스룰·파라미터를 규칙이 읽는다).
   - **게스트 준비 = `readyVersion == configVersion`**. 방장이 룰셋·봇을 바꾸거나 게임이 끝나면 `configVersion`이 1 오르고
     게스트 준비가 저절로 풀린다 — 방장이 게스트 항목을 직접 고칠 일이 없어서 "방장은 사람 항목을 고칠 수 없다"를 규칙으로 걸 수 있다.
   - 저장소는 이전 문서에서 **바뀐 필드만** 바꿔 쓴다(바뀌지 않은 필드가 규칙의 diff에 잡히지 않게).
3. **방 규칙**
   - 만들기: 방장 혼자 앉은 새 방, 정산 완료, 비공개면 같은 배치에서 `joinCodes/{code}` 선점.
   - 게스트: 대기 중에만, **자기 항목만**(입장·준비·퇴장). 입장 = 강퇴되지 않음 + 자리 있음 + 정산 완료 + 준비 안 됨으로 시작.
     준비는 지금 `configVersion`에만(미리 다음 설정에 준비해 둘 수 없음).
   - 방장: **사람은 뺄 수만 있다**(넣거나 고칠 수 없음). 룰셋·봇 변경은 `configVersion + 1` 필수. 시작은 모든 게스트가 지금 설정에 준비했을 때.
     게임 중에는 상태만 바꾼다. 닫힌 방은 얼어 있다. `hostUid`·`visibility`·`joinCode` 등은 바꿀 수 없다.
   - 목록 조회는 공개 방만. 비공개 방 ID는 참가 코드(`joinCodes/{code}`, get만 허용)로만 알 수 있다.
4. **게임 생성은 방에 묶인다**(`games/{id}`의 `roomId`): 방이 이 gameId로 시작됐고, 좌석 = 방의 `memberOrder` 전원(봇 제외),
   `rated` = 방 구성(봇·하우스룰·파라미터 변경 없음), **좌석 전원 정산 완료**. 결과의 `rated`는 게임의 `rated`일 때만.
   -> 게임 좌석은 항상 **스스로 들어온 사람**이고, 남에게 가짜 패배를 씌울 수 없다.
5. 정산 게이트 연결: 방 만들기·입장(클라이언트는 `RoomError.UNSETTLED_GAME`, 규칙도 거절)·게임 생성.
6. 방이 닫히면 저장소가 같은 트랜잭션에서 참가 코드를 푼다.

## 검증
- `RoomStoreTest` 22개: 정상 흐름(만들기 -> 입장 -> 준비 -> 시작 -> 게임 생성 -> 종료), configVersion 준비 해제, 비공개 코드·해제, 공개 목록,
  마지막 자리 경쟁, 정산 게이트, 그리고 조작된 클라이언트의 직접 쓰기(게스트·방장·새 방·참가 코드·게임 생성)를 검사별로 거절.
- 접근 모델(`AccessPolicy`)의 한 줄짜리 검사 89개를 하나씩 끄는 변이 검증: 79개는 해당 테스트가 실패한다. 남은 10개는 다른 검사가 먼저 막는
  중복 방어다(불변 문서 3, 결과 배치는 방장만 2(대기 표시·명령 발신자는 컴파일 구조상 변이 불가 포함), 상태 기계·허용 필드 목록 3, 명단 모양 1, 준비 버전 1).
- 이 과정에서 찾은 실제 위험: **방장이 configVersion을 되돌리면 게스트의 옛 준비가 되살아난다** — "한 번에 +1만" 규칙으로 막고 테스트로 고정.

## 앱이 할 일
- 방장: `RoomService.start(...)`가 돌려준 `GameStartPlan`으로 `FirestoreGameTransport.createGame(plan)` -> `HostGameSession`.
- 모든 사용자: 로비 진입 전에 `FirestoreUserRepository.settlePending()`; `RoomError.UNSETTLED_GAME`이면 정산 후 다시 시도.

## 설계 대비 차이 / 한계
- 비공개 방 입장 시 규칙은 코드를 검사하지 않는다: 방 ID(12자 무작위)를 아는 것 자체가 자격이다. 코드는 ID를 찾는 수단.
- 방장 권위 모델의 한계는 그대로다: 방장은 방에서 합의한 룰셋과 다른 룰로 게임을 돌리거나 순위를 조작할 수 있다(엔진 상태를 규칙이 검증할 수 없음) -> Phase 7.
- 규칙 언어에 반복문이 없어 좌석 6개까지 펼쳐서 검사한다(준비·정산). 최대 인원이 늘면 함께 늘려야 한다.
- 방장의 강퇴 시 `memberOrder` 순서 보존은 규칙에서 검사하지 않는다(보안과 무관; 모양 검사 — 명단 = members — 만 한다).
